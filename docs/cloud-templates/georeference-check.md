# 原圖經緯線對點驗證

2026-11-10 發現台灣雲圖原本錯當經緯度等距矩形。錯誤路徑已移除；台灣與東亞皆先在原圖座標清理、裁切，再依各自投影轉成規則經緯度網格。台灣輸出 800×800、東亞輸出 1200×1200，沒有 400／320 格的降採樣。

投影依據：[CWA 紅外線黑白、彩色及色調強化雲圖產品說明](https://www.cwa.gov.tw/Data/data_catalog/3-7-2.pdf)，2.2.2 節。

- 台灣：橫麥卡托，中央經緯度 `(121,23.7)`，左下 `(116.1417,19.0295)`，右上 `(126.2109,28.2065)`。
- 東亞：Lambert，中央經緯度 `(128.5,0)`、參考緯度 `(30,60)`，左下 `(102.111,-1.503)`、右上 `(155.270,48.589)`。

台灣採 [PROJ 文件的球面橫麥卡托公式](https://proj.org/en/stable/operations/projections/tmerc.html#spherical-form)，原圖範圍以投影後的角點正規化；不是 TWD97/TM2，也不是把緯度直接線性映射到 y。以本機隔離安裝的 PROJ 另行比對公式，並用原圖格線抽查像素定位。球面與 WGS84 形式在本組抽查的差異小於格線線寬；這裡不宣稱有公尺級地面定位精度。

## 測量證據

來源是 2026-11-10 20:40 的兩張 native fileapi 原圖，台灣 800×800、東亞 1200×1200。JPEG SHA-256 與 32 個經緯線控制點保存於 `app/src/test/resources/satellite_control_points.json`，JVM 測試直接使用這些獨立量測的控制點。

台灣控制點為 118／120／122／124°E 與 20／22／24／26°N 的 16 個交點：排除另一條交叉線的中心區，按高亮線芯剖面取中心。東亞控制點為 110／120／130／140°E 與 10／20／30／40°N 的 16 個交點：沿兩條格線的鄰近線段，分別量測白色虛線中心位置。線寬、JPEG 與虛線間隙使中心測量只能作為像素級近似；它們不是測量級地面控制點。

| 方法 | 控制點 | RMS 像素誤差 | 最大像素誤差 |
| --- | ---: | ---: | ---: |
| 台灣舊等距經緯度假設 | 16 | 3.88 | 8.26 |
| 台灣 TM 修正後（含來源像素取整） | 16 | 0.81 | 1.12 |
| 東亞現有 Lambert（含來源像素取整） | 16 | 1.45 | 2.10 |

測試容許台灣 2 像素、東亞 3 像素，涵蓋原圖線寬及像素取整。這個檢查可抓到舊台灣投影的錯位；不能只用同一公式自算預期值當成地理對齊驗證。

## 重現

保留兩張原始 JPEG 在 `build/cloud-debug/native-current/taiwan.jpg`、`east_asia.jpg` 後執行：

```powershell
python -B scripts/check_satellite_georeference.py
```

工具先核對原圖 SHA-256，產出 `build/cloud-georeference/taiwan_report.json`、`east_asia_report.json` 與兩張 `*_source_controls.png`。青色圈為原圖量測中心，綠色十字為修正後來源像素；台灣紅色叉為舊線性假設。這些是未縮放的原圖診斷圖，並非 App 截圖。

原圖 inpaint 後的 `CroppedCloudImage` 保留 left/top 偏移；投影索引永遠使用原始 800／1200 像素座標。已裁掉的標題外框保持缺值，不拉伸回原地理範圍。快取版本 13 會丟棄舊台灣錯誤網格。

本次完成原圖對點、裁切偏移測試、單元測試、組建與 lint。修正版仍須由使用者用 Android Studio Run 部署，並確認底圖 Google logo、道路與標籤載入後，才能判斷手機畫面上的最終疊圖。不能把本機對點結果宣稱為已完成實機驗證。
